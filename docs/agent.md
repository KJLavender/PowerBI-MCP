# Phase 3：MCP Server 與本機問答 Agent

讓使用者直接問「為什麼這個指標下降了」，並且做到：

- **全程不出內網**：MCP Server 是本機子程序（stdio），模型由本機 Ollama 執行。
- **不亂回答**：回答逐項比對工具結果（日期、範圍、數字、名稱、對應、方向、顯著性、原因、重點），不通過就不顯示模型的文字。

```
使用者 ──► agent（本機）──► Ollama（WSL，GPU）
              │  ▲
              ▼  │ 工具結果（JSON，數字已格式化）
        MCP Server（analysis.mcp_server，唯讀，stdio）
              │
              ▼
   Power BI 模型（TMDL/PBIR）＋ DuckDB 每日快照 ＋ Phase 2 分析引擎
```

## 使用方式

### 網頁聊天室（給一般使用者）

雙擊專案資料夾裡的 **`報表問答助理.cmd`**，或直接打開 **http://localhost:8090**。
登入 Windows 時，「PowerBI-Sim Chat」排程會在背景自動啟動伺服器（`scripts\start-chat.ps1`）。

| 網址 | 內容 |
|---|---|
| `http://localhost:8090` | **報表 + 問答**：左邊是 Report Server 上的 Power BI 報表，右邊是問答面板。面板可以收合，也可以拖曳調整寬度 |
| `http://localhost:8090/chat` | 只有問答 |

**對話紀錄**

- 每則問答都存在本機的 `data/chats.sqlite`，不會進 git，也不會離開這台電腦。內容包含回答、查核結果、工具呼叫與證據。
- 重新整理頁面會回到目前的對話；「新對話」會開始新的一段，舊的保留在紀錄中。
- 「紀錄」按鈕會列出過去的對話（標題、時間、問答數），點選即可載入並**接著追問**，也可以刪除。
- 伺服器重啟後，從資料庫還原前文，追問照樣有效；先前工具結果中的數字也仍可作為查核依據。

**報表與問答的連動**

- **篩選列帶動兩邊**：報表上方的篩選列（日期、比較方式、區域、門市、通路、品類、商品、顧客分群）會同時：
  - 以 Report Server 的 URL 篩選參數套用到報表。日期依比較方式顯示比較期間，例如「單日」會顯示到前 4 週。
  - 成為問答的預設範圍。選好「北區、3C配件、2026-09-17」後，直接問「為什麼下降了？」即可。
- **回答帶動報表**：回答完會出現「在報表中查看：北區 × 3C配件（『商品』頁）」按鈕，按下後篩選列與報表都會套用該範圍。建議的頁面是**依 PBIR 報表定義找出的**：看哪一頁的視覺效果最常使用這些維度欄位。
- **網址保存狀態**：篩選狀態會寫在網址的 `#` 後面，可以加入書籤或分享給同事。
- **限制**：
  - Report Server 的嵌入模式不支援用網址切換頁面（`pageName` 無效），所以頁面只能提示，需由使用者點選頁籤。
  - 使用者在報表內點選的交叉篩選，因為瀏覽器跨來源限制，問答面板讀不到；請改用上方的篩選列。

報表是用 `?rs:embed=true` 嵌入 Report Server 的。網址請用 `localhost`，不要用 `127.0.0.1`，因為報表的登入狀態存在 cookie 裡，主機名稱不同時，瀏覽器會把它當成第三方 cookie 擋掉，報表就會一片空白。用 `127.0.0.1` 開啟時，頁面會自動轉址。報表網址可以用環境變數 `REPORT_URL` 更換。

日期可以只寫月份，例如「2026/6」「2026年6月」，工具會解讀成「截至該月最後一天的近 28 日」，並在結果中註明。

- 可以直接追問，例如問完北區之後再問「那南區呢？」，它會記得前面的日期與指標。
- 回答過程會即時顯示正在查什麼（例如「分析變化原因：銷售額，北區，2026-09-17」）。
- 每則回答下方會標示查核結果：**✓ 已通過自動查核**，或 **⚠ 查核未通過，已改為說明原因**；展開「查核明細」可看到每一項比對了幾處、有沒有問題，點「查看證據」可以看到每次工具呼叫的完整結果。
- 伺服器預設只開放本機（`127.0.0.1`）。如果要讓同網段的同事使用，可以改用 `python -m agent.web --host 0.0.0.0`，但資料會在區網內傳輸。
- 所有分頁共用同一個本機模型，問題會依序處理；同時有人在問時，會顯示「排隊中」。

### 命令列

```powershell
.\.venv\Scripts\python -m agent ask "為什麼 2026-09-17 北區的銷售額下降？" -v   # -v 顯示工具呼叫
.\.venv\Scripts\python -m agent chat                                            # 互動模式
.\.venv\Scripts\python -m agent evaluate                                        # 跑題庫評分
.\.venv\Scripts\python -m agent --model qwen3:8b ask "..."                      # 換模型
```

模型預設為 `qwen3.5:4b`（3.4GB），可用環境變數 `AGENT_MODEL` 或 `--model` 更換。
Ollama 位址預設 `http://127.0.0.1:11434`（本機是 WSL 裡的 Ollama 服務，透過 localhost 轉發）。

## 轉寄對話給同事

問答面板上的「轉寄」會產生一個連結（30 天內有效）並打開 Outlook 草稿：信裡列出問了哪些問題、最後的結論、
當時報表的篩選與資料日期，加上連結。

同事點連結，看到的是**同一個報表畫面**（篩選、日期一併套用）和**這段對話的副本**，可以直接接著問；
副本與原本的對話分開，不會互相改到。副本最上方註明「誰在什麼時候轉寄、當時資料截至哪天」，資料之後更新了也會提醒
舊回答的數字是當時的。

- 連結要能從同事的電腦打開：啟動時設定 `PUBLIC_URL`（例如 `http://報表主機:8090`）。
- 目前沒有登入：拿到連結的人就看得到這段對話（報表本身仍由 Report Server 的權限控管）。

## MCP 工具（全部唯讀，`readOnlyHint=true`）

| 工具 | 用途 |
|---|---|
| `describe_model` | 模型中的指標（DAX、說明、拆解關係）、維度（關聯路徑）、資料期間 |
| `list_members` | 某維度的成員名稱，避免模型猜錯名稱 |
| `daily_report` | 某天的每日變動報告（Phase 2 產出） |
| `metric_change` | 指標在某範圍、某日、某時間窗的數值與變化、是否顯著 |
| `explain_change` | **回答「為什麼」**：同範圍其他指標（量／價／折扣／成本）、模型拆解關係、沿各維度的貢獻、是否為更大範圍的現象、節日／新店／資料品質脈絡 |
| `metric_trend` | 時間序列，看何時開始變化 |
| `data_quality` | ETL 狀態、資料量異常的門市 |
| `metric_lineage` | 指標從哪來：DAX、引用量值、實際欄位、報表中的位置 |
| `report_emphasis` | 報表作者的設定：條件式格式門檻、目標線、凸顯的成員，並用最新數字對照作者的門檻（見 [catalog.md](catalog.md)） |
| `explain_visual` | 使用者描述畫面上的某張圖（「紅色的」「北區那根長條」「毛利率那條虛線」）：找出是哪張圖、它顯示什麼、量值怎麼算、作者的規則，以及依報表日期範圍算出的數值與各成員落在哪個顏色；有好幾張符合時列出候選（見 [visuals.md](visuals.md)） |
| `cross_report` | 跨報表：某量值／欄位在其他報表的同義量值、同名不同義、共用來源、代碼比對；兩者之間的關聯路徑；所有報表的總覽 |

輸入錯誤時會回傳可修正的提示，例如「區域沒有成員『北部』。可用成員：中區、北區、南區、東區」，讓模型能自行修正。

### 接到其他 MCP Client

`agent/mcp-config.example.json` 是標準的 `mcpServers` 設定，可以用在：

- **ollmcp**（[mcp-client-for-ollama](https://github.com/jonigl/mcp-client-for-ollama)）、**mcphost**、**Open WebUI**：同樣是全本機執行。
- **使用雲端模型的 MCP Client**（例如 VS Code Copilot）：可以用，但工具結果會送出內網。**只適合用在模擬資料**，不要用在公司的真實資料。

## 如何避免「亂回答」

原則：**工具算，模型只負責說；說出來的每一件事都要能對回工具結果。**驗證分成四層，沒有一層用到另一個 LLM。

```
① 對帳        分析引擎的數字 ＝ Power BI 自己用 DAX 算的數字？          python -m analysis reconcile
② 工具防呆    分析工具本身就給出正確的判讀（重點、量價判讀、樣本不足）
③ 回答查核    每個回答逐項比對工具結果，不過就退回重寫                   agent/grounding.py
④ 查核器測試  刻意竄改正確回答，量測查核器擋下多少                       python -m agent mutation-test
```

### ① 對帳：引擎算的就是報表上的數字

`analysis reconcile` 連到 Power BI Desktop 背景的本機引擎，用 DAX 重算抽樣的數字逐一比對（見 [analysis.md](analysis.md)）。零售 4,176 個、Superstore 5,700 個，**0 個不一致**。這一層確保後面所有查核的「標準答案」本身是對的。

### ② 工具端：讓正確的判讀不需要模型推理

- **重點**：`explain_change` 會附上一句由程式產生的結論，例如「北區 的 銷售額下降 -19.1%，變化偏大；顯著異常的部分：北區 × 3C配件（銷售額 -46.7%）；型態：量減」。系統提示要求結論以它為準。
  - 子範圍只有在「明顯比整體更突出」時才會被點名；各部分同向變化時寫「各部分普遍同向變化，不是集中在單一部分」。
  - 「變化集中在某成員」只在它佔的變動遠大於它平常的比重時才寫（佔一半明細的成員本來就會佔一半的變動）。
- **三級判讀**：顯著異常／變化偏大但未達門檻／在正常波動範圍內；樣本不足時是「樣本太少，無法判斷」。
- **量價判讀**：量、價（同品項價格指數，排除商品組合）、折扣、毛利率的組合，例如「售價與折扣沒變、毛利率下降 → 單位成本上升」。小量資料只列至少「偏大」的變化，避免把雜訊說成「可能是漲價影響買氣」。
- 問比率指標（毛利率）時，不放成本、利潤這類**金額**：金額跟著量變動，模型很容易誤讀成「成本上升」。
- 參數防呆：月份會解讀成整月；超出資料範圍的月份直接報錯（不再默默換成最後一天）；量值存在但翻譯不了時明說「無法計算」，並列在 `describe_model` 的「無法分析的量值」。
- **日期校正**：問題寫了 2015-10-11，模型卻只傳 2015-10 時，呼叫工具前就改回問題的日期，並在結果中註明。

### ③ 回答查核（`agent/grounding.py`）

工具結果帶有給查核器用的結構化事實（`_facts`：哪個範圍、哪個指標、往哪個方向、是否顯著、判讀是什麼；`_key`：必須提到的顯著部分）。這些欄位在交給模型前就拿掉，只給查核器用。每個回答逐句檢查：

| 查核 | 內容 | 擋下的例子 |
|---|---|---|
| 日期 | 問題問的日期，就是工具查的日期 | 問 2015-10-11，查的是 10 月整月 |
| 範圍 | 問題提到的成員，就是工具查的範圍，不多不少 | 問 Furniture，模型自己加上 Europe 去查，答成 Europe |
| 數字 | 每個數字（含日期）都在工具結果中；正負號、百分比要一致 | 自己算出的 -28%、「佔 84%」寫成「-84%」 |
| 名稱 | 每個指標、成員名稱都出現在工具結果中 | 捏造不存在的門市 |
| 對應 | 數字前面寫的成員與指標，要和該數字出現在同一筆工具結果 | 把 3C配件 的 -75,386 說成電商平台的 |
| 方向 | 「X 上升／下降」與 X 的變化方向一致 | 問「為什麼下降」，其實上升 |
| 顯著性 | 「顯著異常」「未達顯著」「正常波動」與該範圍的三級判讀一致 | 把「偏大」說成「正常波動」、把「樣本太少」說成「顯著異常」 |
| 原因 | 資料證明不了的原因（競爭對手、天氣…）只能用「可能／無法判斷」 | 「主要原因是競爭對手大舉促銷」 |
| 重點 | 工具判定能解釋變化的顯著部分，回答要提到 | 漏掉北區 × 3C配件 |

不通過時把問題逐條回給模型重寫，最多 3 次。**仍不通過時，不顯示模型的文字**：若工具已經回答了問題，就改顯示工具自己的判讀（重點、主要數字、深入一層、量價判讀），並註明「語言模型的說明未通過查核」；否則說明哪裡不一致、建議換個問法。網頁上每個回答下方都有「查核明細」，列出每一項比對了幾處、有沒有問題。

查核器本身也會誤判（把正確的句子當成錯誤），這次修掉的例子：「並非顯著變化」「顯著性為 false」這類否定寫法、「低毛利率商品**占比**提高」（方向講的是占比不是毛利率）、「3C 配件」中間多了空格、「而非競爭對手削價」這種排除式的說法。誤判不會讓錯誤答案出去，但會讓好回答被換成工具判讀，所以每次都用評分與突變測試確認。

### ④ 查核器的突變測試（`agent/mutation.py`）

拿評分中查核通過的回答，用 8 種方式刻意改錯（數字竄改、正負號反轉、張冠李戴、捏造名稱、方向反轉、顯著性反轉、無據原因、漏掉重點），每種最多 3 次，用同一份證據再查核一次。不需要模型，結果可重現。沒擋下的例子會列在報告裡（[零售](../reports/mutation-test.md)、[Superstore](../datasets/superstore/reports/mutation-test.md)）。

## 評分結果（`qwen3.5:4b`，RTX 3060 Ti 8GB）

題庫依埋入的情境出題（Agent 看不到情境檔），另有陷阱題：沒有異常的日子、問題方向是反的、不存在的成員、超出資料範圍、資料無法回答的業務原因、可能為負的指標、翻譯不了的量值、刻意小於雜訊的變化。每題要呼叫對的工具、提到正確原因，並通過全部查核。

| | 零售（Oracle，11 題） | Superstore（Excel，15 題） |
|---|---|---|
| **使用者拿到正確答案** | **10～11/11** | **14～15/15** |
| 　模型自己寫對、查核通過 | 9 | 9～11 |
| 　模型被退件，改顯示工具判讀 | 1～2 | 4～5 |
| **查核通過卻答錯** | **0** | **0** |
| 突變測試：竄改後被攔下 | 97～99% | 94～96% |
| 與 Power BI 對帳 | 4,176 個數字，0 個不一致 | 6,140 個數字，0 個不一致 |

範圍是最近幾輪評分的結果（小模型每次輸出不同）。另外，直接從 .pbix 匯入的零售報表（見 [pbix-import.md](pbix-import.md)）：使用者拿到正確答案 10/11、查核通過卻答錯 0、突變測試 97%。

完整紀錄：[零售問答](../reports/agent-evaluation-qwen3.5_4b.md)、[Superstore 問答](../datasets/superstore/reports/agent-evaluation-qwen3.5_4b.md)。

- 小模型每次輸出不同，幾輪之間「模型自己寫對」在 8～12 題之間浮動；「查核通過卻答錯」每一輪都是 0。
- 模型最常被退件的錯誤：把「偏大但未達顯著」「樣本太少」寫成「顯著異常」、自己計算出工具沒有的數字、擅自加上問題沒問的範圍。這些都被查核擋下，改顯示工具判讀。
- Superstore 沒答對的一題：模型擅自加上 Europe 去查 Furniture，查核擋下後，當時的退件流程拿了範圍錯的那次查詢當工具判讀（已修正：只採用範圍與日期都符合問題的查詢）。
- 改進過程中，舊版「只查數字」的查核器讓兩個錯誤回答通過：生鮮題說「有機蔬菜組為顯著異常」（工具判讀是偏大）、VIP 題說「正常波動」（工具判讀是偏大）。新的「顯著性」查核會比對到每一個範圍的三級判讀。

## 已知限制

- **速度**：每題約 15～90 秒。GPU 同時被其他程式（例如遊戲）佔用時會明顯變慢。正式部署建議使用專用 GPU，或換成更大的模型（例如 `qwen3:8b`，需要約 6GB 可用 VRAM）。
- **查核只能檢查「與分析結果一致」，不能檢查「分析選到的是最好的解釋」**：分析工具本身的判讀若有偏差，查核也會放行。所以回答都會附上證據，並用埋入事件的評分與 Power BI 對帳檢查分析本身。
- **題庫各只有 11、15 題**，是針對埋入情境設計的。導入真實資料前，應該用公司過去實際發生過的事件建立題庫，並重跑突變測試。
- **文字查核是規則式的**：靠詞彙、句型找出「誰、什麼指標、往哪個方向、是否顯著」。突變測試仍有 3～6% 的竄改沒被擋下（例如把成員換成清單中另一個同樣出現在證據裡的成員），新的寫法也可能造成誤判；每次修改查核器都要重跑評分與突變測試。
