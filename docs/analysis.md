# Phase 2：每日變動分析

每天自動回答兩個問題：**哪些指標有異常變化？變化來自哪裡？**
所有數字都由程式計算，不使用 LLM。報告中的每一句話都是固定句型套用計算結果，並附上判斷依據。

## 流程

```
Power BI 專案 (TMDL + PBIR) ──► semantic.py ──► 量值公式、關聯路徑、報表用了哪些指標
                                    │
Oracle ──(依關聯自動產生 SQL)──► store.py ──► DuckDB 每日快照 (data/analysis.duckdb)
                                    │
                               engine.py ──► 資料品質 → 變化偵測 → 範圍取捨 → 拆解
                                    │
                               report.py ──► reports/<日期>.md（人看）、data/reports/<日期>.json（Phase 3 Agent 用）
```

| 指令 | 用途 |
|---|---|
| `python -m analysis model` | 顯示從 Power BI 專案讀到的關聯、維度、量值公式、報表用到的指標 |
| `python -m analysis snapshot [--start --end]` | Oracle → DuckDB 快照（預設：重抓最近 3 天＋新日期） |
| `python -m analysis report [--date]` | 產生某天的報告 |
| `python -m analysis daily` | 快照＋昨日報告（每日排程呼叫） |
| `python -m analysis evaluate [--start --end]` | 用 `scenarios.yaml` 的標準答案評分，輸出 `reports/evaluation.md` |
| `python -m analysis reconcile [--port]` | 與 Power BI Desktop 本機引擎用 DAX 算出的數字對帳，輸出 `reports/reconcile.md` |

## 「懂」報表的方式：從模型讀，不寫死

- **量值**：把 DAX 轉成可計算的公式，例如 `毛利率 = DIVIDE([毛利],[銷售額])` → `(銷售額−成本)/銷售額`。時間比較類量值（`CALCULATE`、`TOTALMTD`）會略過，由引擎自己處理期間比較。
- **驅動關係**：`客單價 = DIVIDE([銷售額],[訂單數])` 被解讀成 `銷售額 = 訂單數 × 客單價`，整體銷售額變動時，自動拆成「來客」與「客單價」兩個因素。
- **關聯**：維度欄位一律沿著模型中的多對一關聯 JOIN；`config.yaml` 裡寫了模型不存在的欄位，啟動時就會報錯。
- **分析重點**：只掃描報表頁面上實際出現的量值（從 PBIR 解析），也就是使用者平常在看的指標。
- **訂單層級維度**：由資料自動判斷（每張訂單是否只對應一個值）。區域、門市、通路、顧客分群可以計算訂單數；品類、商品不行，因為同一張訂單會包含多個品類。

## 換一份報表：資料集與資料來源

分析的對象由環境變數 `PBI_DATASET` 決定：預設 `retail`（`powerbi/` + `analysis/config.yaml`，資料來自 Oracle）；其他資料集放在 `datasets/<名稱>/`（Power BI 專案、`analysis.yaml`、問答題庫），例如 `datasets/superstore`（見 [excel-dataset.md](excel-dataset.md)）。快照與報告依資料集分開存放。

- **資料來源跟著模型走**：`semantic.py` 讀 Power Query 分割區，`Oracle.Database(...)` 就連 Oracle；`Excel.Workbook(File.Contents(路徑或參數))` 就把工作表載入記憶體中的 DuckDB（`sources.py`）。兩者用同一套 SQL 產生快照。
- **LEFT JOIN**：對不到維度的事實資料仍計入總數（成員顯示為「(空白)」），和 Power BI 的行為一致。
- **與 Power BI 對帳**：`python -m analysis reconcile` 連到 Power BI Desktop 背景的本機引擎，用 DAX 重算抽樣的數字逐一比對（零售 4,176 個、Superstore 5,700 個，皆 0 個不一致）。

小量資料需要的設定（零售資料不使用，結果不受影響）：

| 設定 | 作用 |
|---|---|
| `thresholds.min_rows` | 本期與比較期間各至少幾筆明細才判斷是否異常；不足時判讀為「樣本太少，無法判斷」 |
| `roles.signed` | 可能為負或接近 0 的指標（例如利潤）不以變化率判斷 |
| `windows.<w>.seasonal: total` | 成員的季節校正改用整體去年同期的變化 |
| `thresholds.pattern_min_z`、`price_index_move` | 量價型態只列至少「偏大」的變化、同品項售價指數超過雜訊才算價格變動 |
| `default_window` | 沒有單日時間窗時，問「某一天」改用哪個時間窗 |
| `variants` + `PBI_VARIANT` | 改讀另一份活頁簿（例如沒有埋入事件的原始資料），用來量測背景誤報 |

## 偵測與取捨規則

| 時間窗 | 比較方式 | 用途 |
|---|---|---|
| 單日 | 當日 vs 近 4 週同星期平均 | 突發事件、資料缺漏 |
| 近 7 日 | vs 前 7 日，扣除去年同期的同一變化 | 近期轉折 |
| 近 28 日 | vs 前 28 日，扣除去年同期的同一變化 | 持續性變化 |
| 近 28 日 vs 去年同期 | 成員的年增率 − 整體**同店**年增率 | 每週只掉一點的慢性流失 |

- **顯著**：與該序列自身過去半年的變化分布相比（穩健 z 值），整體 ≥ 3、維度成員 ≥ 4（成員檢定次數多，門檻較高），且變動幅度夠大。
- **具體 vs 全面**：「北區 × 3C配件」下滑時，如果扣除它之後 3C配件 其他區域都正常，就只報告「北區 × 3C配件」，並註明它解釋了「3C配件」與「北區」的變化；如果多數兄弟成員也同向變動（例如所有飲料都漲價），就改報告較大的範圍「飲料」。
- **跨維度**：北區、南區、VIP 的折扣率上升都來自「官網」時，只報告官網。
- **集中度**：某品類的銷量增加，如果幾乎都發生在某個通路，報告會寫明「變化集中在通路 X」。
- **脈絡註記**：比較期間包含節日、範圍內有新開門市、當日有資料品質問題，都會附註，節日相關的發現排序會降低。
- **新發現 vs 持續中**：14 天內報告過的同一變化，改列在「持續中」，不重複佔用版面。

## 評分（2026-05-15 ～ 2026-10-05，每天完整執行一次）

最新結果見 [`reports/evaluation.md`](../reports/evaluation.md)。

| 情境 | 偵測延遲 |
|---|---|
| 飲料漲價、官網促銷、門市資料缺漏 | 當天 |
| 生鮮成本上漲 | 1 天 |
| 北區 × 3C 配件下滑（3 天內逐步） | 2 天 |
| VIP 緩慢流失（60 天內逐步） | 42 天部分比對（VIP × 日用品），80 天完全比對（VIP） |

每天平均 2 個新發現，其中約 1.2 個無法對應到埋入的情境。抽查後發現它們在資料裡是真實存在的波動（例如小門市單日訂單 +56%），並不是計算錯誤；但從業務角度看是雜訊。

## 已知限制

- **只能說明「變化在哪裡」，不能說明「業務上為什麼」**：報告能指出「北區 × 3C配件 量減 45%」，但無法知道是不是競爭對手在促銷，除非那個原因本身也存在於資料中。
- **慢性變化偵測較慢**：每週變動幅度接近正常波動的趨勢，需要累積數週才會達到顯著。
- **比率指標的範圍判斷**：毛利率、單價這類指標，扣除子集合後會受到組合效應影響，所以改用「兄弟成員是否同向」來判斷，集中度分析也只套用在可加總的指標。
- **門檻是依這份模擬資料調整的**：換成真實資料時，需要用真實事件重新校準 `config.yaml` 的門檻。
