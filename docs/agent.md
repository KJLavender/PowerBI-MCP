# Phase 3：MCP Server 與本機問答 Agent

讓使用者直接問「為什麼這個指標下降了」，並且做到：

- **全程不出內網**：MCP Server 是本機子程序（stdio），模型由本機 Ollama 執行。
- **不亂回答**：回答裡的每一個數字都必須出現在工具結果中，由程式自動查核。

```
使用者 ──► agent（本機）──► Ollama（WSL，GPU）
              │  ▲
              ▼  │ 工具結果（JSON，數字已格式化）
        MCP Server（analysis.mcp_server，唯讀，stdio）
              │
              ▼
   Power BI 模型（TMDL/PBIR）＋ DuckDB 每日快照 ＋ Phase 2 分析引擎
```

## 使用方式

### 網頁聊天室（給一般使用者）

雙擊專案資料夾裡的 **`報表問答助理.cmd`**，或直接打開 **http://localhost:8090**。
登入 Windows 時，「PowerBI-Sim Chat」排程會在背景自動啟動伺服器（`scripts\start-chat.ps1`）。

| 網址 | 內容 |
|---|---|
| `http://localhost:8090` | **報表 + 問答**：左邊是 Report Server 上的 Power BI 報表，右邊是問答面板。面板可以收合，也可以拖曳調整寬度 |
| `http://localhost:8090/chat` | 只有問答 |

報表是用 `?rs:embed=true` 嵌入 Report Server 的。網址請用 `localhost`，不要用 `127.0.0.1`，因為報表的登入狀態存在 cookie 裡，主機名稱不同時，瀏覽器會把它當成第三方 cookie 擋掉，報表就會一片空白。用 `127.0.0.1` 開啟時，頁面會自動轉址。報表網址可以用環境變數 `REPORT_URL` 更換。

日期可以只寫月份，例如「2026/6」「2026年6月」，工具會解讀成「截至該月最後一天的近 28 日」，並在結果中註明。

- 可以直接追問，例如問完北區之後再問「那南區呢？」，它會記得前面的日期與指標。
- 回答過程會即時顯示正在查什麼（例如「分析變化原因：銷售額，北區，2026-09-17」）。
- 每則回答下方會標示查核結果：**✓ 數字已查核**，或 **⚠ 有無法查證的內容**。點「查看證據」可以看到每次工具呼叫的完整結果。
- 伺服器預設只開放本機（`127.0.0.1`）。如果要讓同網段的同事使用，可以改用 `python -m agent.web --host 0.0.0.0`，但資料會在區網內傳輸。
- 所有分頁共用同一個本機模型，問題會依序處理；同時有人在問時，會顯示「排隊中」。

### 命令列

```powershell
.\.venv\Scripts\python -m agent ask "為什麼 2026-09-17 北區的銷售額下降？" -v   # -v 顯示工具呼叫
.\.venv\Scripts\python -m agent chat                                            # 互動模式
.\.venv\Scripts\python -m agent evaluate                                        # 跑題庫評分
.\.venv\Scripts\python -m agent --model qwen3:8b ask "..."                      # 換模型
```

模型預設為 `qwen3.5:4b`（3.4GB），可用環境變數 `AGENT_MODEL` 或 `--model` 更換。
Ollama 位址預設 `http://127.0.0.1:11434`（本機是 WSL 裡的 Ollama 服務，透過 localhost 轉發）。

## MCP 工具（全部唯讀，`readOnlyHint=true`）

| 工具 | 用途 |
|---|---|
| `describe_model` | 模型中的指標（DAX、說明、拆解關係）、維度（關聯路徑）、資料期間 |
| `list_members` | 某維度的成員名稱，避免模型猜錯名稱 |
| `daily_report` | 某天的每日變動報告（Phase 2 產出） |
| `metric_change` | 指標在某範圍、某日、某時間窗的數值與變化、是否顯著 |
| `explain_change` | **回答「為什麼」**：同範圍其他指標（量／價／折扣／成本）、模型拆解關係、沿各維度的貢獻、是否為更大範圍的現象、節日／新店／資料品質脈絡 |
| `metric_trend` | 時間序列，看何時開始變化 |
| `data_quality` | ETL 狀態、資料量異常的門市 |
| `metric_lineage` | 指標從哪來：DAX、引用量值、實際欄位、報表中的位置 |

輸入錯誤時會回傳可修正的提示，例如「區域沒有成員『北部』。可用成員：中區、北區、南區、東區」，讓模型能自行修正。

### 接到其他 MCP Client

`agent/mcp-config.example.json` 是標準的 `mcpServers` 設定，可以用在：

- **ollmcp**（[mcp-client-for-ollama](https://github.com/jonigl/mcp-client-for-ollama)）、**mcphost**、**Open WebUI**：同樣是全本機執行。
- **使用雲端模型的 MCP Client**（例如 VS Code Copilot）：可以用，但工具結果會送出內網。**只適合用在模擬資料**，不要用在公司的真實資料。

## 如何避免「亂回答」

1. **工具算，模型只負責說**：所有數字都由 Phase 2 的確定性引擎算好，並附上格式化文字（例如「銷售額 -46.7%（本期 86,023，比較基準 161,410）」）。模型只需要照抄。
2. **系統提示的規則**：
   - 不可自行計算
   - 問「為什麼」一定要先呼叫 `explain_change`
   - 資料無法證明的業務原因要明說「資料無法判斷」
   - 有資料品質問題時，要先提出來
3. **數字查核（`agent/grounding.py`）**：把回答裡的所有數字抽出來，逐一比對工具結果。
   - 有寫正負號的，正負號也必須一致，例如「佔總變動 77%」不能被寫成「−77%」。
   - 百分比只能對應到百分比。
   - 不合格就要求模型重寫，最多重寫 2 次。仍不合格時，**不顯示模型的回答**，改成顯示「這次無法產生可靠的回答」，附上工具回報的錯誤與換個問法的建議。
4. **題庫評分（`agent/questions.yaml`）**：除了埋入的情境題，還有三種陷阱題：
   - 沒有異常的日子：不能編出原因
   - 問資料無法回答的業務原因：必須說無法判斷
   - 資料缺漏：必須先指出是資料問題

5. **判斷類主張查核**：回答如果寫了「顯著」「正常波動」「流失」這類結論，就必須有呼叫過會做顯著性判斷的工具（`metric_change` / `explain_change`）。否則就退回，要求先呼叫工具。這是因為「數字都對，但從真數字推出錯誤結論」的錯誤，數字查核抓不到。
6. **工具端的防呆**：
   - `explain_change` 會自動「深入一層」，列出顯著的子範圍。
   - 變化判讀分成三級：顯著／偏大但未達門檻／正常。
   - 指標名稱寫錯時，會辨識出裡面的成員名稱，並提示正確的 `filters` 寫法。
   - `metric_trend` 會明確說明「本工具不判斷是否異常」。
   - `explain_change` 會附上確定性的**量價判讀**，例如「價升、量減 → 主要來自漲價」「售價不變但毛利率下降 → 單位成本上升」。售價變化用**同品項價格指數**（Laspeyres 指數：Σp₁q₀ / Σp₀q₀）計算，排除商品組合的影響。單純的平均單價會被組合稀釋：飲料每個品項都漲了 8%，平均單價卻只上升 4.7%。

## 評分結果（`qwen3.5:4b`，RTX 3060 Ti 8GB）

完整問答紀錄見 [`reports/agent-evaluation-qwen3.5_4b.md`](../reports/agent-evaluation-qwen3.5_4b.md)。

| 題目 | 結果 | 回答重點 |
|---|---|---|
| 北區 9/17 銷售額下降 | 通過 | 北區本身未達門檻，但「北區 × 3C配件 −46.7%，z −4.7，顯著異常」，佔總變動 84% |
| 生鮮食品毛利率下降 | 通過 | 售價沒變、毛利率下降 → 成本上升 |
| 飲料毛利率上升 | 通過 | 平均成交單價上升 |
| 官網毛利率下降 | 通過 | 折扣率大增 |
| 高雄左營店大跌 | 通過 | 「極可能是資料缺漏，而非實際營運變化」 |
| VIP 是否流失 | 通過 | 年增 +2.3% 低於整體同店 +6.1%，z −2.4，偏大但未達顯著；VIP × 北區 顯著下滑 |
| 陷阱：正常日問為什麼下降 | 通過 | 指出在正常波動範圍內，沒有編造原因 |
| 陷阱：是不是競爭對手促銷 | 通過 | 資料無法判斷，需業務確認 |
| 10/5 的報告要注意什麼 | 通過 | 被數字查核擋下 1 次，重寫後才通過 |
| 客單價怎麼算 | 通過 | DAX 與來源 |
| 只寫月份：「2026/6 的生鮮食品怎麼下降了」 | 通過 | 解讀為整個 6 月：銷售額 -1.3%，在正常波動範圍內 |

**11/11 通過，所有回答中的數字都能在工具結果中找到。**

改進過程中值得記錄的失敗：

- **只寫月份**：使用者問「2026/6」，模型傳了 `2026-06`，工具只接受完整日期而回報錯誤。模型沒拿到資料仍編出數字，查核器擋下兩次後，最後顯示了一段自我矛盾的回答。修正方式：
  - 工具改成看得懂月份。
  - 系統提示要求「工具報錯時修正參數再查」。
  - 查核最終仍不通過時，不再顯示模型回答，改成誠實的提示。
- **飲料漲價**：模型把毛利率上升歸因於「高毛利商品占比提升」，漏掉了漲價。修正方式是加入量價判讀與同品項價格指數。
- **題目本身依賴日期**：「最近一天」會隨每日資料更新而改變答案，改成固定日期。

- **第一版**：北區那題，模型因為北區本身「不顯著」，就寫成「屬於正常波動」。修正方式是在工具端加入「深入一層」。
- **第一版**：VIP 那題，模型把「VIP」當成指標名稱，查不到之後就宣稱「資料中沒有 VIP 維度」；第二版則只看了趨勢數字，就自行斷言「沒有顯著流失」。這兩個錯誤的數字都是真的，所以數字查核器抓不到。後來加上「判斷類主張查核」與工具端的名稱提示，才修正過來。

## 已知限制

- **速度**：每題約 15～90 秒。GPU 同時被其他程式（例如遊戲）佔用時會明顯變慢。正式部署建議使用專用 GPU，或換成更大的模型（例如 `qwen3:8b`，需要約 6GB 可用 VRAM）。
- **查核只能檢查「有沒有根據」，不能檢查「解讀是否最好」**：例如模型可能漏掉某個重要的子範圍。所以報告與回答都會附上證據，讓人可以自己檢查。
- **題庫只有 10 題**，而且是針對模擬情境設計的。導入真實資料前，應該用公司過去實際發生過的事件建立題庫。
- **文字類的錯誤斷言**只能部分防護：數字查核加上判斷類主張查核，可以擋住最常見的幻覺，但無法保證文字敘述完全正確。
